# SIMLOCK — QA test-execution guide & factory-jig integration notes (O-6)

**Status:** current as of the 2026-08-18 build. This replaces
`simlock-test-execution-guide-v6.pdf` as the document to hand a third-party
doorlock manufacturer or an in-house QA engineer. That PDF was LLM-generated
against a prompt document, not our firmware — see §0 before using anything
from it.

Everything below is written against what is actually built and has run on
real hardware (`blelock/simlock/simlock.ino`) and a real backend
(`ozkit/server/server.js`), not against a spec. Where something is planned
but not built, it's marked **NOT BUILT**, not glossed over.

---

## 0. Why this document exists, and what to ignore from the old one

`simlock-test-execution-guide-v6.pdf` was regenerated by an LLM from a prompt
document (both since deleted). Cross-checking it against the real Tuya
supplier spec and against our own firmware found it self-contradictory and,
in places, describing hardware that doesn't exist:

- Its DPID table (Ch.4), JSON worked example (Ch.11), and UI hex mockups
  (Ch.6/7) give **three different meanings for DP21** — not a typo, three
  unreconciled numbering schemes.
- It invents a **Camera MCU / SPI image-verification module** (Ch.3, Table
  6) that was never part of the SIMLOCK build and isn't referenced anywhere
  else in this project.
- Its N8↔DL-MCU pinout (Table 5: TXD=GPIO5, RXD=GPIO6, SRDY=GPIO3,
  MRDY=GPIO4) **does not match what was built.** See §2 for the real pinout
  — GPIO5/6 are strapping pins on the ESP32-C6 (sampled at boot/reset) and
  would have made the board unreliable to power on with the DL-MCU attached,
  which is very likely why they were moved during the real build.

What the same PDF got right and is safe to reuse as background: the MQTT
topic *names*, the general portal/provisioning UX shape, and the idea of a
50-test traceability suite. Full reasoning: `ozkit/docs/simlock-dp-reconciliation.md`.

## 1. What SIMLOCK is

A fleet QA test-bench: a Waveshare ESP32-C6-N8 dev board running
`blelock/simlock/simlock.ino`, shipped to third-party doorlock manufacturers
so they can validate their DL-MCU firmware against our test fixture before
integration. It talks to the DUT (device under test) over plain UART using
the real Tuya low-power serial protocol, drives a small pre-defined test
suite against it, and reports results both locally (web portal) and
centrally (sealed MQTT telemetry to `ozkit/server`).

**Target DUT profile:** `tuya-luona-ds013-t3` — Luona Smart, Smart Lock
DS013-T3, PID `vr4iiuqtyh0q4nix` (one manufacturer's DP selection per board
build — see §5). No shared/merged DP map across boards.

Confirmed by firmware's own fleet restructure (`XF-122`, 2026-08-20): Tuya DP
numbers are **per-product-category, not universal** — the same DP number can
mean a different thing on a different Tuya lock family (e.g. DP76 is
`unlock_ble` on Luona's map but `fill_light` on Tuya's own Wi-Fi-Lock-Pro
reference map). Firmware deleted the old `tuya-generic-lock` fallback for
exactly this reason — a fixture or lock guessing at an unidentified DP map
can silently execute the wrong command. **Luona is confirmed SIMLOCK's real,
pairable target** — the other candidate vendor, Ladin Tech, remains an
unusable 4-DP stub (`tuya-ladin-f7-t3`, no DP reference ever supplied),
resolving `ozkey-39 §4`'s open "which manufacturer" question in practice.

## 2. Hardware — real pinout

| Signal | N8 GPIO | Direction | Notes |
|---|---|---|---|
| DUT TX (N8 RX) | GPIO11 | DUT → N8 | 9600 8N1 |
| DUT RX (N8 TX) | GPIO10 | N8 → DUT | 9600 8N1 |
| SRDY (active-low) | GPIO18 | DUT → N8 | handshake, **off by default** |
| MRDY (active-low) | GPIO19 | N8 → DUT | handshake, **off by default** |
| GND | GND | — | common reference |
| Status LED | GPIO8 | — | RGB, board status (see §7) |
| Factory-reset button | GPIO9 (BOOT) | — | hold 5s |

There is no camera module, no SPI peripheral, no GPIO3/4/5/6 involvement.
GPIO16/17 are this board's USB-CDC/console bridge pins and are not exposed
to the DUT connector.

**SRDY/MRDY handshake:** built and wired, but **disabled by default**. The
firmware talks plain UART (TX/RX/GND only) unless explicitly toggled on:

```
GET  /api/dut/handshake          # returns current on/off state
POST /api/dut/handshake?on=1     # enable
POST /api/dut/handshake?on=0     # disable
```

Enable it only if the DUT is a physical MCU emulator that actually drives
those two lines. Against LockSim (§9) or a plain-UART DUT, leave it off —
enabling it against a DUT that never asserts SRDY will hang every send.

## 3. Provisioning (first boot)

1. Power the board. It boots into AP mode, SSID **`SIMLOCK`**, and shows a
   status LED (amber = booting, cyan-blink = AP mode).
2. Connect a phone/laptop to that AP, browse to `http://192.168.4.1`
   (**http, not https** — the portal is plain HTTP; typing a bare IP into a
   mobile browser sometimes tries `https://` first and silently fails, so
   the `http://` prefix must be explicit).
3. Enter the real Wi-Fi credentials on `/config`. The board joins the real
   network **while staying on the SIMLOCK AP** (dual AP+STA), and the
   confirmation page shows the board's real new IP directly — no `.local`
   hostname lookup required (mDNS has no support on Android
   Chrome/Firefox, so `simlock.local` is not a dependable fallback; the
   board also sets DHCP hostname `simlock` as a secondary option only).
4. Status LED turns green once MQTT connects. Red-blink means Wi-Fi is up
   but MQTT is down.
5. Factory reset: hold the BOOT button (GPIO9) for 5 seconds, or send the
   MQTT `factory_reset` command (§6). Both clear all NVS state — Wi-Fi
   credentials, the board's identity keypair, everything — and restart into
   AP mode.

`GET /api/version` returns `{"fw":"simlock-0.1","profile_id":"tuya-luona-ds013-t3","firmware_id":"fw-tuya-luona-ds013-t3-r2","board_id":"N8-XXXXXX"}` — use this to confirm a board is alive and which manufacturer profile it's running. `firmware_id` is the same canonical id doorlock reports at enrol (`XF-123`), generated once from `profiles/` — useful for tracing a QA run back to an exact catalogue revision.

**Which manufacturer profile a bench issues over UART is operator-selectable, locally, on `/config`** — a dropdown over the profiles already compiled into the board (`tuya-luona-ds013-t3`, `tuya-wifi-lock-pro`, `tuya-ladin-f7-t3`-stub), calling `ozProfileSelect()` and persisting to NVS. No reflash, no network dependency — the DP tables are already onboard. `POST /api/profile?id=<id>` is the underlying REST call; `GET /api/profile` lists what's available. 🔴 **The 15-test seed suite is hardcoded to `tuya-luona-ds013-t3`'s DP semantics** (DP 76 = unlock_ble, etc.) — switching to a different profile changes what the board *reports* itself as, not which DPs the seed suite issues. `/config` shows a warning whenever the active profile isn't the one the suite was written against. A profile-driven seed suite is future work.

## 4. Device identity & sealed telemetry

Every board's MQTT payloads (`status`, `log`, `alert`, `test/start`,
`test/result`, `test/complete`) are **sealed** (AES-256-GCM under an
ECDH-derived key), not plaintext JSON, once provisioned. Rationale: a shared
MQTT password baked into every unit's firmware is trivially extractable via
`esptool read_flash` + `strings`, and one leaked unit compromises the whole
fleet's telemetry, not just itself. This mirrors the same identity model
doorlock already uses in production (`docs/ozkey-34.md`), with `ozkit/server`
playing the role the app plays for a doorlock — courier between NEXUS and
the device.

**Flow:**

1. `ozkit/server` sees a board on `test/boards/+/status` or `.../connection`
   that isn't yet in its own `boards` table.
2. It calls NEXUS `POST /api/v1/dev/lock-keys` with the board's full MAC
   (tagged `app_id: "ozkit-server"` — audit-only, doesn't segregate the row
   from real doorlock rows, see the note at the end of this section) and
   gets back `{pub, priv}` for that board — idempotent per MAC, safe to
   retry.
3. It `POST`s `{"pub":..., "priv":..., "server_pub":...}` to the board's own
   `/api/provision_key` (over the board's real IP, learned from its own
   heartbeat). The board verifies `pub` actually derives from `priv` before
   accepting, caches it to NVS, and computes the shared ECDH secret once.
4. From then on, every publish is sealed under a key derived via
   HKDF-SHA256 (salt = `board_id + "ozkit"`, info =
   `"ozkit/board->server"`), with a NVS-persisted monotonic counter
   preventing nonce reuse across reboots.
5. `ozkit/server` unseals on receipt and serves the decrypted current state
   via `GET /api/boards/:id`.

**Verified property, checked against a real bug doorlock hit:** doorlock's
factory reset *mints a new keypair* locally, which silently invalidates
whatever key NEXUS has on file for that MAC (`nexus-14`, the bug that led to
NEXUS's new `/rekey` endpoint). SIMLOCK's factory reset does **not** do
this — it wipes the board's *local copy* of its keys (`prefs.clear()`) but
never self-mints. Re-provisioning after a reset re-fetches from NEXUS's
`dev/lock-keys`, which is idempotent per-MAC and returns the *same* keypair
every time. So a reset board just re-provisions to its original identity —
there is no rekey-drift case to handle here, and `/rekey` is not something
`ozkit/server` needs to call.

**Known gap, not yet raised as a ticket:** NEXUS's `dev/lock-keys` endpoint
records `app_id` for logging only — it is not written into the
`lock_registry` row. So SIMLOCK test-kit MACs and real doorlock MACs are
indistinguishable in that table by query, only by grepping NEXUS's console
history. Small in practice (few SIMLOCK boards exist), but worth flagging to
NexusPM if fleet accounting there ever gets built out.

If a board's key hasn't been provisioned yet, it falls back to a loudly-logged
plaintext publish rather than failing silently — this is the only case where
telemetry is readable on the wire, and it only happens before first
provisioning succeeds.

## 5. DP catalogue — the real scope boundary

Reconciled from the actual Tuya supplier spec (`docs/DPSuppliers/`), not the
old PDF. **19 DPs are `confirmed`** (known type and byte layout — safe to
test); **15 are `reserved`** (type known, but the supplier doc never
specified payload byte layout, so no codec can be honestly written against
them — tracked as `ozkey-27` Q2, a supplier question).

The seed test suite (`kSeedSuiteCount` = 15 cases today, expandable toward
the eventual 50) reflects this split directly — full list, current build:

| # | Test | DP | Status |
|---|---|---|---|
| 1 | Autolock ON | 23 | runs |
| 2 | Autolock OFF | 23 | runs |
| 3 | Autolock delay = 30s | 24 | runs |
| 4 | Set volume: normal | 21 | runs |
| 5 | BLE switch ON | 42 | runs |
| 6 | WiFi strategy: DTIM10 | 156 | runs |
| 7 | Observe: battery report | 45 | runs |
| 8 | Observe: bolt state report | 47 | runs |
| 9 | Observe: alarm report | 60 | runs |
| 10 | Observe: duress report | 98 | runs |
| 11 | Open Door (Direct Unlock) | 10 | **blocked — ozkey-27 Q2, RAW layout not supplied** |
| 12 | Add PIN credential | 16 | **blocked — ozkey-27 Q2** |
| 13 | Delete PIN credential | 17 | **blocked — ozkey-27 Q2** |
| 14 | Add RFID credential | 13 | **blocked — ozkey-27 Q2** |
| 15 | Delete RFID credential | 14 | **blocked — ozkey-27 Q2** |

Blocked cases return `unsupported` in the suite summary, not a false pass or
a guess. **This is not "we tested a dozen DPs" — it is these exact 19 vs.
these exact 15**, and the 5 blocked cases above (the credential/unlock
group) are the ones that matter most for real-world use, so treat the
`unsupported` count as the headline number, not the pass count.

A firmware/server-side alert also fires automatically on a passing DP60
(alarm) or DP98 (duress) response during any test run — not a separate test,
a side-effect check layered on whichever test happens to trigger it.

## 6. MQTT — topics and payload shapes

Broker: `mqtt.ebizco.com.au:8883` (TLS), dedicated to ozkit — **not** the
lab broker other services use. Client ID = board ID (`N8-XXXXXX`).

| Topic | Direction | Sealed? | Fires |
|---|---|---|---|
| `test/boards/{id}/connection` | out (LWT) | plaintext | connect/disconnect (retained) |
| `test/boards/{id}/status` | out | sealed once provisioned | heartbeat |
| `test/boards/{id}/log` | out | sealed | ad-hoc INFO/WARN/ERROR lines |
| `test/boards/{id}/alert` | out | sealed | DP60 alarm / DP98 duress hit |
| `test/boards/{id}/test/start` | out | sealed | suite run begins |
| `test/boards/{id}/test/result` | out | sealed | once per test case |
| `test/boards/{id}/test/complete` | out | sealed | suite run ends, carries the summary |
| `test/boards/{id}/command` | **in** | plaintext JSON | remote control (below) |

`connection` is deliberately left plaintext — it's a fixed LWT payload set
once at connect time, not worth sealing.

**Remote command channel** (`{"action": "..."}`, plaintext JSON in):

| `action` | Effect |
|---|---|
| `start_test` | runs the full seed suite, same as `POST /api/tests/run` |
| `restart` | `ESP.restart()` |
| `factory_reset` | clears all NVS (Wi-Fi + identity), restarts into AP mode |
| `check_ota` | logs "no OTA mechanism implemented yet" — **NOT BUILT** |
| anything else | logged as unknown, no-op |

**Verified live** (2026-08-18): a full suite run against a real board
produced exactly 1 `test/start`, 15 `test/result` (matching the seed count),
and 1 `test/complete` message, all sealed — confirmed by capturing raw MQTT
traffic and counting per-topic message bytes, not just eyeballing the log.

## 7. Local web portal & REST API

Everything here is served directly by the board over plain HTTP, no cloud
dependency — the portal works even if the MQTT broker is unreachable.

| Page/route | Purpose |
|---|---|
| `/` | portal root — status + IP |
| `/config` | Wi-Fi provisioning + manufacturer profile picker |
| `/live` | run the seed suite, watch results populate live |
| `GET /api/version` | fw version, profile id, firmware_id, board id |
| `GET /api/profile` | every profile compiled in, with the active one flagged |
| `POST /api/profile?id=` | switch the active profile, NVS-persisted, local only (§3) |
| `POST /api/provision_key` | identity provisioning (§4), called by `ozkit/server` |
| `GET/POST /api/dut/handshake?on=` | toggle SRDY/MRDY (§2) |
| `POST /api/lock/unlock` | manual single-DP unlock test |
| `POST /api/credential/pin/otp` \| `/duration` \| `/permanent`, `/api/credential/rfid/read` | manual single-credential tests — **currently target RESERVED DPs, so these will report unsupported until ozkey-27 Q2 is answered** |
| `GET /api/tests/list` | seed suite definition, as JSON |
| `POST /api/tests/run` | run the full suite (also fires the MQTT telemetry sequence in §6) |
| `POST /api/tests/run_one` | run a single case by id |
| `/api/ota/check` \| `/status` \| `/update` \| `/rollback` | all stubbed, HTTP 501 — **no OTA mechanism exists on this board today** |

Status LED (GPIO8, RGB): amber=booting, cyan-blink=AP mode, green=MQTT
connected, red-blink=Wi-Fi up/MQTT down.

## 8. `ozkit/server` — the fleet backend

Node/Express on port **5400**, DB `ozkit` on the shared lab MySQL. Not a
dashboard yet — REST only.

| Route | Returns |
|---|---|
| `GET /api/boards` | all known boards, last-seen status |
| `GET /api/boards/:id` | one board's current decrypted status |
| `GET /api/version` | server build info |

`boards` table: `mac` (PK), `board_id`, `board_pub_hex`, `provisioned_at`,
`last_ip`, `last_seen_at`, `last_status` (JSON, decrypted). Provisioning and
unsealing logic per §4.

**Operational note:** the NEXUS credential
(`SUPPORT_BEARER_TOKEN`/`NEXUS_SERVER_KEY` equivalent for the dev-mode
endpoint) currently lives only in the running process's environment — a
restart needs it re-exported, or provisioning of new boards silently no-ops.

## 9. In-house validation status — **BLOCKED, do not treat as validated**

**Task explicitly not completed.** Pointing a SIMLOCK board's DUT UART at
`locksim` proves wire/framing correctness only — `locksim/hooks/useLockState.ts`
is still hardcoded to an old, invented DP map (`DpId.ADD_TEMP_PIN` etc.),
not wired to the real profile's DP semantics. So a "pass" against LockSim
today does not mean the real supplier DP behavior was exercised.

This is flagged, not fixed — `locksim/` ownership between ozkit and firmware
hasn't been settled, and it's a shared directory neither team edits
unilaterally. Before relying on LockSim as an in-house reference DUT,
confirm `useLockState.ts` has been repointed at `profiles/products/*.json`.

## 10. What's NOT built (say this plainly to a manufacturer, don't gloss)

- **OTA** — every `/api/ota/*` route and the `check_ota` MQTT command are
  stubs. There is no over-the-air update mechanism today.
- **5 of 15 seed tests** (the credential/unlock group, DP 10/13/14/16/17) —
  blocked on the supplier answering `ozkey-27` Q2, not a firmware gap.
- **Central web dashboard** — `ozkit/server` is REST-only; no UI yet.
- **Physical DL-MCU emulator validation** — SRDY/MRDY wiring exists and is
  toggleable, but has not yet been exercised against real emulator
  hardware (only against LockSim's plain-UART path, itself blocked per §9).
- **Camera MCU / image verification** — never existed. Do not carry this
  forward from the old PDF into any manufacturer-facing conversation.
